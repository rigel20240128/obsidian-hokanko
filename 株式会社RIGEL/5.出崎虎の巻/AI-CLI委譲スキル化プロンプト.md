# Claude Codeに「他のAIへ仕事を任せる力」を授けるセットアップ指示書

> **このファイルの使い方（人間向け・ここだけ読めばOK）**
>
> 1. Claude Codeを起動する
> 2. このファイルを添付（またはファイルパスを伝える）して、こう言う：
>    **「中身を読んでスキル化して」**
> 3. あとはClaude Codeが自動で進めます。必要なツールが入っていなければ
>    **インストールもClaude Codeが代わりにやってくれます**。
>    途中で「〇〇してください」と言われたら、その通りに操作してください。
>
> **そもそも「CLIツール」って何？**
> CLIは「コマンドライン・インターフェース」の略で、要するに
> **黒い画面（ターミナル）に文字を打って操作するタイプのアプリ**のことです。
> ChatGPTやGeminiは普段ブラウザで使いますが、実は各社が
> 「ターミナル版のAI」も出しています。それがGemini CLI（Google製）、
> Codex CLI（OpenAI製）、Grok CLI（xAI製）です。
> Claude Code自身もCLIツールの仲間です。
>
> CLI版の何が良いかというと、**AI同士を連携させられる**ことです。
> ブラウザ版のGeminiにClaude Codeから仕事を頼むことはできませんが、
> CLI版のGeminiなら、Claude Codeが裏で起動して仕事を頼めます。
>
> **これで何ができるようになる？**
> セットアップ後は、Claude Codeに「**Geminiに聞いて**」と言うだけで、
> Claude Codeが裏でGemini CLIを動かし、結果を受け取って報告してくれます。
> - Claude側の利用枠を節約できる（Gemini側はGoogleの利用枠を消費。
>   **Google AI Pro契約があればその枠がそのまま使えます**）
> - 別のAIのセカンドオピニオンがもらえる（設計判断・原因調査に強い）
> - Codex CLIやGrok CLIを持っていれば、それらも同じように使えるようになります
>
> **事前に用意するもの**：Googleアカウント（Google AI Pro契約があるとベター）だけ。
> Gemini CLIのインストールはClaude Codeが手伝ってくれるので不要です。

# ここから下はClaude Codeへの指示

あなた（Claude Code）は、この指示書に従って**AI CLI委譲スキル**をセットアップする。

**最重要の前提：ユーザーはAIコーディングツールの初心者。**
- 各ステップの前に「今から何をするか」を専門用語なしの日本語で一言説明すること
- エラーが出ても慌てさせない。「よくあることです」と伝えて対処すること
- ユーザーに操作を頼むときは、コマンドをコピペできる形で1つずつ示すこと

## 全体の流れ

1. **検出**：どのAI CLIがインストール済みかを調べる
2. **導入**：Gemini CLIが無ければ、ユーザーの同意を得てインストールする
3. **検証**：CLIの動作・ログイン状態・フラグ仕様を確認する（ログインはユーザーが実施）
4. **生成**：CLIごとに委譲スキル（SKILL.md）を作成する
5. **テスト**：簡単な質問を実際に投げて疎通確認する
6. **説明**：使い方チートシートをユーザーに渡す

## Step 1: 検出

まずユーザーに「お使いのパソコンに何が入っているか調べますね。調べるだけなので
何も変わりません」と伝えてから、以下を確認する：

```bash
command -v gemini; command -v codex; command -v grok
ls /Applications/ChatGPT.app/Contents/Resources/codex 2>/dev/null
ls ~/.local/bin/gemini ~/.local/bin/grok ~/.local/bin/codex 2>/dev/null
command -v node; command -v npm; command -v brew
```

- **Gemini CLIが見つかった場合**：Step 2をスキップしてStep 3へ。
- **Codex / Grokが見つからない場合**：スキップして構わない。
  「Codex（ChatGPTのCLI）やGrok（xAIのCLI）も入れれば同じ仕組みで使えます」と
  一言だけ伝え、無理に導入は勧めない（Gemini CLIとは別の有料契約が必要なため）。

## Step 2: Gemini CLIの導入（未インストールの場合）

ユーザーはおそらくGemini CLIを入れていない。**これは普通のこと**なので、
「Gemini CLIというGoogle公式の無料アプリを入れます。Google AI Proの契約が
そのまま使えます」と説明し、同意を得てから以下の優先順でインストールする。
コマンドの実行はすべてあなたが代行し、ユーザーには結果だけ報告する。

1. **Homebrewがある場合**：`brew install gemini-cli`
2. **Node.js（npm）がある場合**：`npm install -g @google/gemini-cli`
   - 権限エラー（EACCES）が出たら `sudo` に頼らず、npmのグローバル先を
     ユーザー領域へ変える方法（`npm config set prefix ~/.npm-global` ＋ PATH追記）で解決する
3. **どちらも無い場合**：先にNode.jsを入れる。Homebrewも無い環境なら、
   ユーザーに https://nodejs.org/ja から「LTS版」をダウンロードして
   インストーラーをダブルクリックしてもらうのが最も安全（GUIで完結する）。
   完了を待ってから 2. を実行する。

インストール後、**新しいシェルでもPATHが通っているか**を確認する
（`command -v gemini`）。通っていなければ `~/.zshrc` へのPATH追記を提案し、
同意を得てから追記する。

ユーザーが導入に同意しなければ全体を中止し、導入方法だけ伝えて終了する。

## Step 3: 検証とログイン

見つかった／導入した各CLIについて：

1. `<cli> --version` でバージョン確認
2. `<cli> --help` を読み、**この指示書末尾のテンプレートに書かれたフラグが
   実在するか必ず照合する**。CLIはバージョンアップでフラグが変わるため、
   テンプレートを鵜呑みにせず、実際のヘルプに合わせて調整すること
3. ログイン状態を確認する（例：Geminiは簡単な質問をヘッドレスで投げてみる、
   Codexは `codex login status`、Grokは `grok models`）
4. **未ログインなら、あなたは絶対に認証を代行しない。** ユーザーに依頼して待つ。
   Geminiの初回ログインは、次の手順をそのまま読み上げて案内すること：

   > これからGeminiに一度だけログインします。手順は3つです。
   > 1. ターミナル（今この画面）とは**別のターミナルウィンドウ**を開いて、
   >    `gemini` と打ってEnterを押してください。Geminiの画面が起動します
   > 2. 認証方法を聞かれたら「**Login with Google**」を選んでください。
   >    ブラウザが自動で開くので、**Google AI Proを契約している
   >    Googleアカウント**でログインして「許可」を押してください
   > 3. ターミナルに戻って画面が使える状態になったら成功です。
   >    `/quit` と打って（またはCtrl+Cを2回押して）終了し、
   >    私に「終わったよ」と教えてください

   ログイン完了の報告を受けたら、ヘッドレスで軽い質問を投げて認証が
   通ったことを自分で確認してから次へ進む。

## Step 4: スキル生成

CLIごとに `~/.claude/skills/<名前>-delegate/SKILL.md` を作成する。
（例：`~/.claude/skills/gemini-delegate/SKILL.md`）

- 内容はこの指示書末尾のテンプレートをベースに、Step 3で確認した
  実際のフラグ・パス・モデル名へ調整して書くこと
- **「安全ガード」の節はどのCLIでも削らずに残すこと**（初心者保護のため）

## Step 5: 動作テスト

各スキル作成後、read-only（読み取り専用）の設定で軽い質問を1つ投げて
疎通確認する。例：

```bash
gemini -p "1+1は？数字だけ答えてください。"
```

応答が返ればOK。タイムアウトやエラーの場合は、ヘルプを見直してスキル内の
コマンド形を修正してから再テストする。**動くことを確認できていない
コマンド形をスキルに残さないこと。**

## Step 6: 使い方の説明

最後に、ユーザーへ以下を伝えて終了する：

1. **新しいスキルを認識させるため、Claude Codeを一度再起動してください**
2. 使い方は、普段の会話でこう言うだけ：
   - 「**Geminiに聞いて**：〇〇ってどう思う？」（セカンドオピニオン）
   - 「**Geminiにレビューさせて**」（コードの確認）
   - 「**Geminiに調査させて**：〇〇のやり方」
   - Codex / Grokを設定した場合は「Codexに聞いて」「Grokに聞いて」も同様
3. 注意点2つ：
   - AIに渡した文章やコードは各社（Google / OpenAI / xAI）のサーバーへ
     送られます。**仕事の機密や顧客情報を含むフォルダを扱うときは注意**
   - 別AIの答えも間違うことがあります。最終判断は自分で

# Gemini委譲

Claudeがオーケストレーターのまま Gemini CLI を裏で走らせ、結果だけ受け取る。
消費は Google アカウントの利用枠。Claude側トークンは減らない。

## 前提

- バイナリ：`{{ command -v gemini の結果 }}`。PATHに無いBashセッションでは絶対パスで呼ぶ。
- 呼び出しは必ず **`-p`（`--prompt`・ヘッドレス）** を付ける。付けないと対話TUIが起動して固まる。
- 認証が切れていたらユーザーに `gemini` の対話起動での再ログインを依頼する（Claudeは認証しない）。
- 実行時間は数十秒〜数分。Bashの timeout は 300000ms 以上。重い依頼は run_in_background。
- モデル指定は `-m <モデル名>`（例：{{ 検証時に確認した利用可能モデル。速い=flash系、難しい調査=pro系 }}）。
- Claude側の会話文脈は自動では渡らない。背景・現象・試したことを依頼文に具体的に書くほど精度が上がる。

## 安全ガード（必須）

- 委譲＝依頼文やコード断片を Google のサーバーへ送ること。機密・顧客情報を含む
  素材を読ませる委譲は、ユーザーの明示的な発話（「Geminiに聞いて」等）がある場合のみ行う。
- 読むだけの依頼が基本。書き込みを伴う依頼は {{ --approval-mode 等、検証した安全な編集許可フラグ }} を
  使い、完了後に必ずdiffを確認する。
- `--yolo`（全自動承認）は使わない。外向き操作（公開・送信・削除・支払い）は任せない。
- 結果は鵜呑みにせず、Claude自身で妥当性を確認してから報告する。
- **シークレットのコミット防止**：依頼文ファイル・結果ファイルはリポジトリ外（`/tmp` 等）に
  置くのが基本。リポジトリ内に置く必要がある場合や、CLIが設定フォルダ（`.gemini/` 等）を
  リポジトリ内に作った場合は、機密が含まれ得るため**先に `.gitignore` へ追加**してから使う。

## 呼び出し形

作業ディレクトリはBashのcwdがそのまま使われる。

```bash
# 調査・セカンドオピニオン（読むだけ）
gemini -p "次の問題を調査して意見をください。<背景・現象・試したこと>"

# コードレビュー（読むだけ）
gemini -p "次の変更をレビューしてください。観点: <バグ/セキュリティ等>"

# 実装・修正（書き込みあり・要ユーザー同意）
gemini -p "<実装指示>。変更したファイル一覧を最後に報告してください。" {{ 編集許可フラグ }}
```

- 長い結果は `> 結果ファイル` にリダイレクトして実行後にRead。

## 🔴 ハマりどころ

1. **`-p` 忘れ＝対話画面が起動してハング。** ヘッドレスは必ず `-p`。
2. **ヒアドキュメント同居禁止**：`cat > 依頼文 << EOF` と `gemini -p "$(cat 依頼文)"` を
   同じBash呼び出しに書くと変数が空になりハングし得る。長文依頼は
   ①Writeツールで依頼文ファイルを作る → ②別のBash呼び出しで実行、の2段に分ける。
3. 無料枠にはレート制限がある。連続で投げてエラーが出たら少し待って再実行する。

## 返答方針

実行したコマンドと使ったモデル名を伝え、Geminiの結果を要約し、
Claude自身の見立て（採用/不採用の判断）を添える。
````

# Codex委譲

Claudeがオーケストレーターのまま Codex CLI を裏で走らせ、結果だけ受け取る。
消費は ChatGPT プランの利用枠。Claude側トークンは減らない。

## 前提

- バイナリ：`{{ 検出したパス。ChatGPT.app同梱版があればそちらを優先 }}`
- ログイン確認は `codex login status`。切れていたらユーザーに `codex login` を依頼する（Claudeは認証しない）。
- 実行時間は数十秒〜数分。Bashの timeout は 300000ms 以上。重い依頼は run_in_background。

## 安全ガード（必須）

- 委譲＝依頼文やコード断片を OpenAI のサーバーへ送ること。機密・顧客情報を含む
  素材を読ませる委譲は、ユーザーの明示的な発話がある場合のみ行う。

  `danger-full-access` は使わない。

- **シークレットのコミット防止**：依頼文ファイル・`-o` の結果ファイルはリポジトリ外（`/tmp` 等）に

## 呼び出し形

```bash
# 調査・セカンドオピニオン（read-only）
codex exec --skip-git-repo-check -s read-only -C <対象ディレクトリ> -o <結果ファイル> \
  "次の問題を調査して意見をください。<背景・現象・試したこと>"

# コードレビュー（gitリポジトリなら専用コマンド・読み取り専用）
cd <リポジトリ> && codex review --uncommitted

# 実装・修正（workspace-write・要ユーザー同意）
codex exec --skip-git-repo-check -s workspace-write -C <対象ディレクトリ> -o <結果ファイル> \

```

- `-o <file>`：Codexの最終メッセージがそのファイルに書かれる。実行後にReadして要約報告する。

## 🔴 ハマりどころ（実測済みの事故）

1. **ヒアドキュメント同居禁止**：`cat > 依頼文 << EOF` と `codex exec "$(cat 依頼文)"` を

   必ず ①Writeツールで依頼文ファイルを作る → ②別のBash呼び出しで実行、の2段に分ける。
2. **起動ハング検知**：バックグラウンド実行時は発注2〜3分後に `-o` ファイルのサイズを確認。
   出力ゼロならハング＝停止して再発注する。

## 返答方針

実行したコマンド（sandbox・対象ディレクトリ）を短く伝え、結果を要約し、Claude自身の見立てを添える。
````

# Grok委譲

Claudeがオーケストレーターのまま Grok CLI を裏で走らせ、結果だけ受け取る。
消費は X Premium / grok.com のサブスク枠。Claude側トークンは減らない。

## 前提

- バイナリ：`{{ 検出したパス }}`
- 認証確認は `grok models`。切れていたらユーザーに `grok login` を依頼する（Claudeは認証しない）。
- 呼び出しは必ず **`-p`（ヘッドレス）** を付ける。付けないと対話TUIが起動して固まる。
- 実行時間は数秒〜数分。Bashの timeout は 300000ms 以上。重い依頼は run_in_background。

## Grokに投げると得なもの

- **X（旧Twitter）とWebのリアルタイム情報**：「今この話題はどう言われているか」の
  一次情報収集は他CLIより強い。
- **セカンドオピニオン**：設計判断・原因切り分けを別系統モデルに当てる。

## 安全ガード（必須）

Grokのヘッドレスは**既定でフルツールアクセス**を持つ。必ず絞ること。

- **読むだけの依頼**：`--sandbox read-only` ＋ `--tools "read_file,grep,list_dir"` を付ける。
- **書き込みを伴う依頼**：`--sandbox workspace --always-approve`。完了後に必ずdiffを確認。
- サンドボックス無指定＋`--always-approve` の組み合わせは使わない。
- 委譲＝依頼文やコード断片を xAI のサーバーへ送ること。機密・顧客情報を含む素材を
  読ませる委譲は、ユーザーの明示的な発話がある場合のみ行う。
  素材を送りたくない一般質問では `--cwd /tmp` にして作業フォルダを触らせない。
- 外向き操作（公開・送信・支払い・削除）は任せない。
- **シークレットのコミット防止**：依頼文ファイル・結果ファイルはリポジトリ外（`/tmp` 等）に
  置くのが基本。リポジトリ内に置く必要がある場合や、CLIが設定フォルダ（`.grok/` 等）を
  リポジトリ内に作った場合は、機密が含まれ得るため**先に `.gitignore` へ追加**してから使う。

## 呼び出し形

```bash
# 一般質問・セカンドオピニオン（作業フォルダを触らせない）
grok -p "<背景・現象・試したこと>。原因の候補と切り分け手順を挙げてください。" \
  --cwd /tmp --sandbox read-only --tools "read_file,grep,list_dir" --output-format plain

# X/Webのリアルタイム調査（Grokの本領）
grok -p "<調べたいテーマ>について、X上とWebで直近どう語られているか。出典URL付きで要点を。" \
  --cwd /tmp --sandbox read-only --output-format plain
```

## 🔴 ハマりどころ

1. **`-p` 忘れ＝TUI起動でハング。** ヘッドレスは必ず `-p`。
2. **`--tools` のツール名は内部ID。** シェルは `bash` ではなく `run_terminal_cmd`。
3. **`--sandbox read-only` のネットワーク遮断はLinuxのみ。** macOSでは効かないので、
   外部送信を止めたいときは `--disable-web-search` を付ける。
